### 2. A newer autosave throws away the one in flight, so on large projects autosaves can keep being dropped and never reach the store

**confirmed / major / data-loss** — `src/persist/autosave.ts:10` (area: persist-export)

**FIXED 2026-09-30** in `486c971` (branch `fix/review-batch-a`).

- **Problem:** saveAutosave bumps the generation when it starts and drops its own result if another save has started meanwhile (`if (started !== persistGeneration()) return;`). Every autosave re-encodes every key cell (collectFrameAssets, one toBlob per cell), which on a long iPad project can take many seconds. App.svelte starts a new save 3 s after each edit (plus the 1.5 s pen-quiet wait), and the hide flush (App.svelte:450-453) starts one at once. Whenever the gap between edits is longer than about 3 s but shorter than the encode time, each save is dropped before it writes, and the IndexedDB copy stops advancing for as long as that rhythm lasts. A dropped save also resolves normally, so onAutosaveOk (App.svelte:306) clears a failure warning even though nothing was written. The hide flush can likewise discard a timed save that was almost done and replace it with one that has to start over just as iOS is about to suspend the page. The generation also serves pruneMedia (media-store.ts:25-31), so any autosave that starts aborts a prune that is still running.
- **Scenario:** Take a 1200-key-cell project on iPad where one encode takes about 10 s. The artist draws a stroke, pauses 4-6 s to look, and draws again. Each timed save starts, then the next edit's save supersedes it before its IDB put, so nothing is written for the whole session. If the tab is killed, the reload restores work from long before. No warning is shown, and any earlier 'Autosave is failing' warning was cleared by a dropped save.
- **Suggested fix:** Run one save at a time: while a save is in flight, mark it dirty and start exactly one follow-up when it finishes, rather than abandoning the snapshot. Keep the generation drop only for a document replace (New/Open/restore), with a separate counter from the one pruneMedia checks. Have saveAutosave report 'superseded' so the caller does not treat it as success.
- **Verifier:** autosave.ts:9-14 bumps the generation at start and returns before the IDB put when another save has started, so the newer save wins and the older snapshot is thrown away. saveProjectBlob awaits one toBlob per key cell, so a large project takes seconds. The timer (3 s after the last edit plus 1.5 s pen-quiet) can start a new save while the last one is still encoding, and the hide flush always starts a fresh full encode, dropping one that was nearly done just before suspension. A dropped save resolves normally, so onAutosaveOk clears persistAlert although nothing was written. Nothing is lost for good once the user pauses longer than one encode, but a tab killed during a steady editing rhythm, or during the hide flush, loses more work than it should.

### 3. Redo throws away a moved selection or pasted float, which cannot be undone

**confirmed / major / data-loss** — `src/state/appState.svelte.ts:2669` (area: state-undo)

**FIXED 2026-09-30** in `f96b3fe` (branch `fix/review-batch-a`).

- **Problem:** undo() (2637-2661) stops early when `liftGuard.hasEdits()` is true: it cancels the live transform and returns, because 'the transform itself [is] gone for good' otherwise. redo() (2669-2678) has no such check. It calls `liftGuard.discard?.()`, which runs `discardActiveEdits`, i.e. `selection.cancel()` / `cancelPose()` (Canvas.svelte 2687-2690), and then goes on to `history.redo()`. A lift or paste pushes no history entry (Canvas.svelte 1650, 1753-1770), so the redo stack is still full while a float is live. redo() also skips undo()'s early return for a live Outline preview, so the redo cancels the preview and applies the next step in the same press.
- **Scenario:** Draw stroke A, then press Cmd+Z (A is now on the redo stack). Select a region and drag it somewhere else, or paste a copied region and move it. Press Cmd+Shift+Z by mistake (or tap three fingers). The float is cancelled: the moved or pasted pixels go back or vanish. Stroke A comes back. The move cannot be recovered, because Cancel pushes no undo step.
- **Suggested fix:** Give redo() undo()'s guard: `if (liftGuard.hasEdits?.()) { liftGuard.discard?.(); return; }`. Or apply the lift (`bank`) and stop, since Apply is undoable. Also mirror undo()'s outline-active early return.
- **Verifier:** redo() (appState 2669-2678) calls liftGuard.discard?.() and continues with no hasEdits/outline early return. undo() has both. discardActiveEdits (Canvas 2687-2690) runs selection.cancel()/cancelPose()/cancelOutline(). pasteSelection (Canvas 1753+) and the lift push no history entry, so the redo stack survives a live float, and Toolbar/App/touch redo all reach redo(). A moved selection or pasted float is silently cancelled, and that cannot be undone.

### 5. Pose Apply erases every pixel the silhouette mesh does not cover: small separate details, the right and bottom 1px rim, chopped corners, thin strokes

**confirmed / major / data-loss** — `src/core/triangulate.ts:98` (area: transform)

**FIXED 2026-09-30** in `51dd21b, a07cb99` (branch `fix/review-batch-a`).

- **Problem:** enterPose clears the whole content rect out of the cell (`selection.liftPixels`, Canvas.svelte:2032). applyPose then paints back only `meshPose.render(selCtx)` (Canvas.svelte:2072), and that draws only the mesh triangles (mesh-pose.ts:217-227, each one clipped to its own triangle in `drawTriangle`). The mesh does not cover the silhouette, for four reasons. (1) Vertices sit at integer pixel indices (mesh-pose.ts:139), which are pixel top-left corners, so the right-most column and bottom-most row of ink are always outside the hull. (2) `boundaryPoints` decimates greedily in scan order (triangulate.ts:24-41), so real corners are often not kept and the hull cuts chords across them. (3) Triangles are kept only if their centroid is inside (triangulate.ts:98), so strokes thinner than `spacing` mostly produce no triangles. (4) A separate island smaller than about `spacing` (an eye dot, a speckle) produces no triangle at all. Measured with the real `triangulateSilhouette` at the default spacing 16, testing pixel centres against the triangles: a solid 100x60 rect leaves 6.3% uncovered (corner wedges about 20px wide plus the right and bottom rim); a disc r=40 leaves 4.9%; a 3px diagonal line 72%; a 3px ring 92%; a 9px dot beside a big disc 100% (49/49 px). Pixels with alpha 1-10 are also outside the `inside` predicate. Unverified in a browser: each triangle's own anti-aliased clip may also leave faint seams along shared edges.
- **Scenario:** Draw a character with a small separate eye dot and some thin hair strokes. Choose Pose, drag one handle a little, then Apply (or switch tool). The dot and most of the thin strokes are gone from the cell, and the outline has lost its right and bottom outer pixel row. The loss shows in the preview, but it is easy to miss at small sizes, and it is baked on Apply.
- **Suggested fix:** Make the mesh cover the whole lift: use pixel-corner or pixel-centre-plus-0.5 vertices, always keep the extreme and corner boundary pixels, and push boundary vertices out about 1px. Or add a fallback pass that draws every lifted pixel outside all triangles with the affine of its nearest triangle or vertex, or refuse Apply when coverage is below 100% of the lifted alpha. Add a coverage unit test.
- **Verifier:** enterPose runs liftPixels, which clears the whole content rect from the cell. applyPose paints back only meshPose.render, and each triangle is clipped to its own triangle in drawTriangle (selection.ts:1207). Nothing else draws the lifted pixels back. Vertices sit at integer pixel indices, mapped as rect.x + v.x/dpr, so the last column and row are outside the hull. boundaryPoints decimates greedily in scan order, and triangles are kept only when their centroid is inside (triangulate.ts:98). So small islands under about the spacing and thin strokes get no triangles, and their pixels are lost on Apply. I did not re-run the finder's coverage percentages, but the mechanism is in the code.

### 9. Canvas resize ignores layer and group transforms, so transformed art moves

**confirmed / major / correctness** — `src/state/appState.svelte.ts:2250` (area: state-undo; also found by ui-input)

**FIXED 2026-10-01** in `ab7229c` (branch `fix/review-batch-b`).

*As reported by the state-undo reviewer:*

- **Problem:** `resizeProject` bakes each cell's own transform into its pixels, 'so resize preserves the transformed look' (commit 442bbe4). It leaves `layer.transform`, `group.transform` and every transform-track key untouched. Those values are document pixels relative to the target's centre: `RefTransform.dx/dy` is 'translate from fit-center, document logical px', and for a drawing layer the base rect is the whole document (document.ts 478). Scale mode shrinks or grows the pixels but keeps dx/dy, so every translated layer lands off by (1-s)·dx. In crop mode with an off-centre anchor, the pivot (the document centre) moves relative to the art, so any scaled or rotated layer shifts. Reference layers get the same stale dx/dy against a recomputed contain-fit. The changelog records a stale `track.box` / `transformBox` as a known hazard. It says nothing about the transform values themselves.
- **Scenario:** Crop case: a 1000x1000 document with a layer at scale 2 and dx=dy=0. A dot at (600,500) shows at 700. Resize to 2000x1000, crop, anchored left: the pixels stay put, but the centre moves to 1000, so the dot now shows at 1000+2·(600−1000)=200. Scale case: a layer at dx=100 with a centred dot shows it at 600. Scale to 500x500: the dot's pixel moves to 250, but it shows at 350 instead of 300. Animated layers and groups drift the same way on every key.
- **Suggested fix:** In the same commit, map each draw or reference layer's static transform and track keys, and each group's transform, transformBox and track.box, through the placeContent rect. In scale mode, scale dx/dy by rect.w/oldW. In crop mode, move the pivot. The simpler alternative is to refuse or warn when any layer or group has a non-identity or animated transform.
- **Verifier:** resizeProject (2230-2269) replaces only key-cell canvases (baking the per-cell transform) and sets width/height. layer.transform, group.transform/transformBox and the transform tracks are untouched. transformBaseRect gives a draw layer the whole document as its base, so the pivot is the document centre and dx/dy are document px. ### 40. Running audio is not re-synced after an fps change, a ripple insert/delete, or trim-to-playhead during playback

**confirmed / minor / correctness** — `src/lib/Playbar.svelte:42` (area: timeline)

**FIXED 2026-10-01** in `01c3811` (branch `fix/review-batch-e`). commitStructural re-syncs only when the commit moved the track, its offset or its trim.

- **Problem:** `audioEngine` schedules the buffer once at play/sync time from the fps, offset and trim of that moment. ### 43. Brush cursor ignores layer or group scale; strokes on a scaled layer draw wider or narrower than the ring
